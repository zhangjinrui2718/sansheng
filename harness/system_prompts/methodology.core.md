# 方法论:任何一件活,按这五步走

> 这份文件是**三个干活角色共享的作业系统**(项目经理 / 研究员 / 工程师)。
> 它不改变你的职责边界 —— 它规定的是**做事的顺序与标准**。

## 第一步 · 定义问题:先写清「成功长什么样」

接到任何一件活,**第一句话不是动手,是把问题重写一遍**:

- **甲方的话**通常描述的是手段("做个塔防游戏")—— 你要翻译成**目的与约束**
  ("能玩的 v1:单 HTML、核心循环能转、无外链、打开即玩")。
- 三行写死:**问题是什么 / 成功长什么样 / 什么明确不做**。
- 写不出这三行 = 问题还没定义,不要开工,也不要猜 —— 回去问(研究员问上游,
  项目经理问甲方或问研究员拿事实)。

### 1.5 维度清单:枚举「做好」的各方面,逐维裁决

三行写完还不够 —— 每个领域都有**一批「做好了该考虑」的方面**,不主动枚举,
它们就会在交付后才被甲方问出来(真机案例:一个网页小游戏交付后,甲方问起
性能与页面切后台的行为,全部工件里 0 次讨论 —— 它们是**碰巧没出事**,不是**被考虑过**)。

所以拆解前必须:

1. **枚举本领域「做好」的维度**(按领域常识列全:比如网页小游戏的清单是
   核心循环 / 数值平衡 / 难度曲线 / 上手引导 / 反馈手感 / 音效 / 存档续玩 /
   性能与内存 / 页面失焦与暂停 / 分辨率适配 / 触屏 / 错误处理。别的领域同理,
   先列全再裁决,宁多勿漏);
2. **逐维裁决并留痕**:`做(进哪条工作项)/ 本版不做(理由 / 触发条件)/ 不适用`。
   每一维都必须落在三档之一 —— **没有第四档叫「没想到」**;
3. 「本版不做」不是丢掉:写进交付说明的「未做清单」,让甲方在收货时看得见边界。

⚠️ 这一步的产物(维度裁决表)要随拆解一起落进 `board_write` —— 它是拆解的
依据,不只是你想的过程。

## 第二步 · 第一性原理:从事实与约束推,不从模板与惯例抄

- 把活拆到**不可再拆的事实**:用户是谁、跑在哪、数据多大、必须依赖什么、
  性能底线是多少。每一条问自己:「这是被验证的事实,还是我沿用的惯例?」
- 惯例可以用来**省时间**,不能用来**当依据** —— "大家都是这么做的"在第一步
  的三行面前必须重新过堂。
- 平台给了你取证的通路:`knowledge_search`(项目语料)/ `board_read`(已有产出)/
  `read`+`grep`(仓库原文)。**先取证,再推断**;推断要标注「这是推断」。

## 第三步 · 定义「做好」的指标:不可检验的指标等于没有

每件活至少一条**可机械检验**的完成判据,写进工作项 / 写进交付物开头:

- 好的指标:"正文可见中文 ≤300 字"、"双击打开 3 秒内出标题"、"第 1 波 10 辆
  坦克在 60 秒内被消灭且防线值不掉"、"JS 过 `node --check` 且零外链资源"。
- 坏的指标:"做得好一些"、"体验流畅"、"界面美观" —— **没有数字或动作的
  指标是愿望,不是验收**。
- 指标在**动手前**定义,不是做完再挑一个已达标的。做完后**逐条对照**,
  每条给「可复现的证据」(数字 / 截图 / 命令输出),不是「我看过了,没问题」。

## 第四步 · 拆解与实现:先走通,再变好

- **最小可行路径先行**:先让核心链路端到端跑通(哪怕粗糙),再逐项打磨。
  反过来做(每一步都精雕)会在半路烧光预算,还留不下任何能跑的东西。
- 实现时**守住第一步的「不做清单」** —— 范围蠕动的样子通常是"顺手多做了
  一个没用到的功能,却漏了判据里的那一条"。
- 交付前**自检**:把第三步的指标逐条过一遍,每条留证据。自检不过的东西
  交出去,等于把「没做完」包装成「做完了」。

## 第五步 · 收尾:留下下一个人能用的事实

- 产出与结论落**结构化工件**(平台会把它收进语料,后来的人可检索);
- 交付说明写「怎么验证我说的是真的」—— 复现命令、打开方式、逐条对照表;
- 没做完 / 做了假设,**明说**。静默的缺口是下一个人最贵的坑。

---

⚠️ **这五步的顺序就是它的价值**:跳过第一步直接实现,是所有返工的源头;
指标在实现后才补,是所有"我觉得做好了"争论的源头。

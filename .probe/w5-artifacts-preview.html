催收对话「听+说」耦合度高(用户抢话、Bot 抢话、节律都需要并发感知),模式 A 把耦合度放在模型内部,通道侧保持简单 - 模式 B 看似灵活,实则把「音频上文」「语义上文」「节律上文」全部推到通道层管理,工程复杂度远超模式 A **前提:** Qwen-Omni 全双工模式在 DashScope API 调用形态下支持所需的并发度。若实测不支持,则退到模式 B。 — 这一选择属于本模块的**关键技术决策 #1**,见 §十。 ### 2.2 接入拓扑 - **输入方向:** 通道侧持续把分片音频送入模型输入流(经 DashScope 流式 API) - **输出方向:** 通道侧持续从 DashScope 流式响应中读取音频分片,推给 TTS 输出端 - **状态方向:** 模型自身维护对话上文(包括音频上文);通道侧不持有对话状态,只持有「传输态」(流 ID、时钟、缓冲水位) **通道侧不解释音频含义** — 它只搬运。这是它能保持简单、且与基础打断/节律感知解耦的关键。 --- ## 三、流式音频组织(回答 ① — 「音频如何组织」) ### 3.1 输入分片策略 | 参数 | 建议值 | 理由 | |---|---|---| | 采样率 | 16kHz 单声道 | 语音对话标准;低于 16kHz 损失高频辅音,高于则带宽浪费 | | 帧长(物理帧) | 20ms | 通用 VoIP 帧长,与 RTP 标准对齐 | | 分片(逻辑 chunk) | 100ms / 5 物理帧 | 太小则 DashScope 调用频繁(开销↑),太大则首 token 等待变长 | | 分片缓冲 | 自适应 80–120ms | 网络抖动时自动调整,以「稳定节奏」喂模型 | **为什么是 100ms 而不是 200ms 或 50ms:** - 50ms:DashScope 调用频次翻倍,首 token 改善有限 - 200ms:首 token 多等 100ms,催收对话下用户能感觉到「Bot 反应慢」 - 100ms:实测上是语音流式模型的甜区(**这是经验值,非选型结论;落地时需结合 DashScope 实际行为调测**) ### 3.2 输出分片策略 | 参数 | 建议值 | 理由 | |---|---|---| | 模型输出粒度 | 音频 token 流(DashScope 流式响应) | 由模型侧产出节奏决定 | | 通道侧输出帧 | 20ms 物理帧,与输入对齐 | 与 VoIP 接收端对齐,免去重采样 | | 输出缓冲 | 60–80ms FIFO | 让用户感觉「自然连续」,避免分片感 | ### 3.3 双向时钟 - **输入时钟:** 远端 RTP 时间戳(单调递增) - **输出时钟:** 本机生成的输出时间戳(由 DashScope 流式产出节奏驱动) - **两端不同步** — 这是全双工的固有特性,不需要做时钟对齐 - **通道侧只做单调性检查:** 检测 RTP 时间戳乱序、重传 ### 3.4 流式输入/输出协议契约 | 契约 | 字段 | 说明 | |---|---|---| | `audio_chunk_in` | stream_id, seq, sample_rate, samples(pcm16), timestamp | 上游送入,本模块消费 | | `audio_chunk_out` | stream_id, seq, sample_rate, samples(pcm16), bot_tts_id | 本模块产出,下游(TTS 端)消费 | | `vad_event` | stream_id, state(start/end), confidence, timestamp | 本模块产出,VAD 事件 | | `tts_play_state` | stream_id, state(playing/paused/aborted), bot_tts_id | 本模块产出,广播给订阅方 | 这些是**通道与外界的接口契约**,所有数字字段在本模块内做严格单调性 / 越界 / 错位校验。 --- ## 四、首包延迟目标与瓶颈分析(回答 ②) ### 4.1 首包延迟定义 「首包延迟」= 用户说完一句话后,到 Bot 第一个音频 token 被 TTS 输出端接收为止的时间。 — 这是催收对话「自然不卡顿」的体感指标。 ### 4.2 目标 **首包延迟 ≤ 800ms**(经验阈值,用户感知「对方在思考」而非「对方卡了」的下限)。 **争取 ≤ 600ms**(若 DashScope 首 token 性能可达成)。 ### 4.3 瓶颈拆解(量化估计,假设 DashScope 云 API 部署形态) | 环节 | 估计时延 | 是否可优化 | |---|---|---| | 前端 RTP 解包 + VAD 帧 | 20–40ms | 受前端硬件限制,优化空间小 | | 流式音频分片缓冲(等齐 100ms) | 80–120ms | **可调** — 调小分片可压到 50ms,但 DashScope 调用频次上升 | | **DashScope 模型推理首 token** | **300–500ms** | **主要瓶颈** — 占整个延迟的 50%+,**由 DashScope 服务端决定,本架构侧不可干预** | | 首段音频解码 + 重采样 | 20–40ms | 与 TTS 选型耦合,本模块不评估 | | 网络回传(本机 ↔ DashScope 服务端) | 20–60ms | 受网络与 DashScope 区域选择影响 | | **合计** | **440–760ms** | — | ### 4.4 瓶颈结论(回答 ②,云 API 部署形态下) **最大瓶颈是「模型推理首 token」**,占端到端首包延迟的 50%+。 — 网络、前端均可控;模型推理延迟由 **DashScope 服务端**决定,**本架构侧不可干预**。 — 链路走通阶段降低首 token 延迟的杠杆: - **VAD 由本模块内置:** 通道侧运行轻量级 VAD(声学帧级,见基础打断 §二中的 VAD 阈值) - **VAD 事件广播:** 本模块把 `vad_event` 同时分发给基础打断、节律感知、对话 NLU 三个下游 - **不强求一致:** 各下游可以基于自己的需要做二次判定(基础打断有 400ms 候选窗口,见基础打断 §三) ### 5.2 对话管理协同 - **对话状态机的载体是对话主流程,** 不在本模块 - **本模块向状态机上报的事件:** - `user_turn_started` / `user_turn_ended`(基于 VAD 聚合) - `bot_turn_started` / `bot_turn_ended`(基于 TTS 播放状态) - **本模块从状态机接收的事件:** - `end_call`(通话终止) - 其它控制事件(略,非本模块核心) ### 5.3 与基础打断的协同(契约兑现) 兑现基础打断 §七 中约定的契约: | 流向 | 契约 | 协议字段 | |---|---|---| | 本模块 → 基础打断 | TTS 播放状态广播 | `tts_play_state: {state: playing/paused}` | | 基础打断 → 本模块 | 暂停/恢复指令 | `tts.pause(stream_id, last_sentence_idx)` / `tts.resume(stream_id, from_sentence_idx)` | | 本模块 → 基础打断 | 音频流(单写多读) | `audio_chunk_in` 复制品 | | 本模块 → 基础打断 | VAD 事件 | `vad_event` | 本模块收到 `tts.pause` 后的动作: 1. 立即停止从 DashScope 流式响应中读取音频分片(本模块侧冻结) 2. 广播 `tts_play_state: paused` 3. 等待 `tts.resume` 后,从 `from_sentence_idx` 对应的输出流位置继续读取 --- ## 六、模型推理部署折衷(回答 ③) ### 6.1 吞吐 vs 延迟 vs 成本(三角权衡) ``` 低延迟 /\ / \ / \ / \ / ★ \ / 折衷点 \ / \ /______________\ 高吞吐 ←———————→ 低成本 ``` - 催收对话「听+说」耦合度高(用户抢话、Bot 抢话、节律都需要并发感知),模式 A 把耦合度放在模型内部,通道侧保持简单 - 模式 B 看似灵活,实则把「音频上文」「语义上文」「节律上文」全部推到通道层管理,工程复杂度远超模式 A **前提:** Qwen-Omni 全双工模式在 DashScope API 调用形态下支持所需的并发度。若实测不支持,则退到模式 B。 — 这一选择属于本模块的**关键技术决策 #1**,见 §十。 ### 2.2 接入拓扑 - **输入方向:** 通道侧持续把分片音频送入模型输入流(经 DashScope 流式 API) - **输出方向:** 通道侧持续从 DashScope 流式响应中读取音频分片,推给 TTS 输出端 - **状态方向:** 模型自身维护对话上文(包括音频上文);通道侧不持有对话状态,只持有「传输态」(流 ID、时钟、缓冲水位) **通道侧不解释音频含义** — 它只搬运。这是它能保持简单、且与基础打断/节律感知解耦的关键。 --- ## 三、流式音频组织(回答 ① — 「音频如何组织」) ### 3.1 输入分片策略 | 参数 | 建议值 | 理由 | |---|---|---| | 采样率 | 16kHz 单声道 | 语音对话标准;低于 16kHz 损失高频辅音,高于则带宽浪费 | | 帧长(物理帧) | 20ms | 通用 VoIP 帧长,与 RTP 标准对齐 | | 分片(逻辑 chunk) | 100ms / 5 物理帧 | 太小则 DashScope 调用频繁(开销↑),太大则首 token 等待变长 | | 分片缓冲 | 自适应 80–120ms | 网络抖动时自动调整,以「稳定节奏」喂模型 | **为什么是 100ms 而不是 200ms 或 50ms:** - 50ms:DashScope 调用频次翻倍,首 token 改善有限 - 200ms:首 token 多等 100ms,催收对话下用户能感觉到「Bot 反应慢」 - 100ms:实测上是语音流式模型的甜区(**这是经验值,非选型结论;落地时需结合 DashScope 实际行为调测**) ### 3.2 输出分片策略 | 参数 | 建议值 | 理由 | |---|---|---| | 模型输出粒度 | 音频 token 流(DashScope 流式响应) | 由模型侧产出节奏决定 | | 通道侧输出帧 | 20ms 物理帧,与输入对齐 | 与 VoIP 接收端对齐,免去重采样 | | 输出缓冲 | 60–80ms FIFO | 让用户感觉「自然连续」,避免分片感 | ### 3.3 双向时钟 - **输入时钟:** 远端 RTP 时间戳(单调递增) - **输出时钟:** 本机生成的输出时间戳(由 DashScope 流式产出节奏驱动) - **两端不同步** — 这是全双工的固有特性,不需要做时钟对齐 - **通道侧只做单调性检查:** 检测 RTP 时间戳乱序、重传 ### 3.4 流式输入/输出协议契约 | 契约 | 字段 | 说明 | |---|---|---| | `audio_chunk_in` | stream_id, seq, sample_rate, samples(pcm16), timestamp | 上游送入,本模块消费 | | `audio_chunk_out` | stream_id, seq, sample_rate, samples(pcm16), bot_tts_id | 本模块产出,下游(TTS 端)消费 | | `vad_event` | stream_id, state(start/end), confidence, timestamp | 本模块产出,VAD 事件 | | `tts_play_state` | stream_id, state(playing/paused/aborted), bot_tts_id | 本模块产出,广播给订阅方 | 这些是**通道与外界的接口契约**,所有数字字段在本模块内做严格单调性 / 越界 / 错位校验。 --- ## 四、首包延迟目标与瓶颈分析(回答 ②) ### 4.1 首包延迟定义 「首包延迟」= 用户说完一句话后,到 Bot 第一个音频 token 被 TTS 输出端接收为止的时间。 — 这是催收对话「自然不卡顿」的体感指标。 ### 4.2 目标 **首包延迟 ≤ 800ms**(经验阈值,用户感知「对方在思考」而非「对方卡了」的下限)。 **争取 ≤ 600ms**(若 DashScope 首 token 性能可达成)。 ### 4.3 瓶颈拆解(量化估计,假设 DashScope 云 API 部署形态) | 环节 | 估计时延 | 是否可优化 | |---|---|---| | 前端 RTP 解包 + VAD 帧 | 20–40ms | 受前端硬件限制,优化空间小 | | 流式音频分片缓冲(等齐 100ms) | 80–120ms | **可调** — 调小分片可压到 50ms,但 DashScope 调用频次上升 | | **DashScope 模型推理首 token** | **300–500ms** | **主要瓶颈** — 占整个延迟的 50%+,**由 DashScope 服务端决定,本架构侧不可干预** | | 首段音频解码 + 重采样 | 20–40ms | 与 TTS 选型耦合,本模块不评估 | | 网络回传(本机 ↔ DashScope 服务端) | 20–60ms | 受网络与 DashScope 区域选择影响 | | **合计** | **440–760ms** | — | ### 4.4 瓶颈结论(回答 ②,云 API 部署形态下) **最大瓶颈是「模型推理首 token」**,占端到端首包延迟的 50%+。 — 网络、前端均可控;模型推理延迟由 **DashScope 服务端**决定,**本架构侧不可干预**。 — 链路走通阶段降低首 token 延迟的杠杆: - **服务商选择:** 评估 DashScope 服务等级 / 区域 / 服务质量(选最近接入点、稳定等级) - **调用参数优化:** streaming mode、prompt 压缩、请求体构造(影响 DashScope 服务端排队与首 token 等待) - **不在通道侧部署形态选择上**(已由外决 #4 锁定为云 API) — 进一步压低首 token 延迟的**部署侧杠杆**(持续批处理、量化、自托管)留作自托管阶段的评估项(见 §六.3 #4 备选) ### 4.5 一句话回答 ② > **瓶颈在 DashScope 模型推理首 token(300–500ms,占 50%+,本架构不可干预);前端 + 网络 + 分片缓冲合计 ~150–260ms,优化空间有限。链路走通阶段只能在服务商选择与调用参数上做优化,部署侧杠杆留给后续自托管评估。** --- ## 五、与 VAD/对话管理的协同方式 ### 5.1 VAD 协同 - **VAD 由本模块内置:** 通道侧运行轻量级 VAD(声学帧级,见基础打断 §二中的 VAD 阈值) - **VAD 事件广播:** 本模块把 `vad_event` 同时分发给基础打断、节律感知、对话 NLU 三个下游 - **不强求一致:** 各下游可以基于自己的需要做二次判定(基础打断有 400ms 候选窗口,见基础打断 §三) ### 5.2 对话管理协同 - **对话状态机的载体是对话主流程,** 不在本模块 - **本模块向状态机上报的事件:** - `user_turn_started` / `user_turn_ended`(基于 VAD 聚合) - `bot_turn_started` / `bot_turn_ended`(基于 TTS 播放状态) - **本模块从状态机接收的事件:** - `end_call`(通话终止) - 其它控制事件(略,非本模块核心) ### 5.3 与基础打断的协同(契约兑现) 兑现基础打断 §七 中约定的契约: | 流向 | 契约 | 协议字段 | |---|---|---| | 本模块 → 基础打断 | TTS 播放状态广播 | `tts_play_state: {state: playing/paused}` | | 基础打断 → 本模块 | 暂停/恢复指令 | `tts.pause(stream_id, last_sentence_idx)` / `tts.resume(stream_id, from_sentence_idx)` | | 本模块 → 基础打断 | 音频流(单写多读) | `audio_chunk_in` 复制品 | | 本模块 → 基础打断 | VAD 事件 | `vad_event` | 本模块收到 `tts.pause` 后的动作: 1. 立即停止从 DashScope 流式响应中读取音频分片(本模块侧冻结) 2. 广播 `tts_play_state: paused` 3. 等待 `tts.resume` 后,从 `from_sentence_idx` 对应的输出流位置继续读取 --- ## 六、模型推理部署折衷(回答 ③) ### 6.1 吞吐 vs 延迟 vs 成本(三角权衡) ``` 低延迟 /\ / \ / \ / \ / ★ \ / 折衷点 \ / \ /______________\ 高吞吐 ←———————→ 低成本 ``` - **低延迟区:** DashScope 高等级服务 / 自托管单请求不批 — 成本最高 - **高吞吐区:** DashScope 标准服务 / 大 batch — 延迟上升,成本最低 - **折衷点:** DashScope 持续批处理(由 DashScope 服务端内部承担,本架构观测即可) **推荐:** 链路走通阶段,持续批处理由 DashScope 服务端内部承担(关键技术决策 #2),本架构仅做观测。自托管阶段才需要本架构侧关心批处理调度。 ### 6.2 上下文窗口 vs 内存 | 策略 | 窗口长度 | 显存占用 | 适用 | |---|---|---|---| | 全保留 | 全通话(可能 5+ 分钟) | O(分钟数) | 不推荐 — 催收单通 3–10 分钟 | | 滑动窗口 | 最近 30–60s 原始特征 | O(常数) | **推荐 — 催收对话的「近因效应」足够** | | 摘要压缩 | 每 30s 做一次隐式摘要 | O(摘要数) | 备选 — 显存更省但工程复杂 | **推荐滑动窗口(关键技术决策 #3):** - 理由:催收对话中,Bot 的回应主要依赖「最近几秒」的用户发言 + 全文语义;音频上下文的「远因」可以通过文本上文(由 DashScope 维护的对话上文)补偿 - 备选:若 DashScope 显存极度紧张(模型侧约束),采用摘要压缩;但会增加 ~50ms 的摘要推理开销,挤压首 token 延迟预算 ### 6.3 自托管 vs API 调用(链路走通阶段已由外决为云 API) | 方案 | 延迟 | 成本 | 灵活性 | |---|---|---|---| | 自托管(GPU) | **低(可控)** | 高(CAPEX + OPEX) | 高 | | **调云 API(DashScope)** | 中(受 DashScope 服务等级与排队影响) | **低(按量)** | 低(链路走通阶段) | **推荐:链路走通阶段先云 API(DashScope 调 Qwen-Omni)(关键技术决策 #4):** - 理由(链路走通阶段):甲方明确以「(便宜)」标注 — 成本是首要驱动;先以最快达成链路为目标,自托管 + INT8 量化作为链路稳定后的成本/可控性优化选项 - 备选:自托管 GPU + INT8 量化 — 链路走通后,若首 token 实测延迟不满足 ≤800ms 预算,启动自托管评估;届时走 `change_propose` - 阶段切换条件:链路稳定 + 成本可控性诉求出现 + 首 token 实测不达标 = 启动自托管评估 ### 6.4 量化等级(链路走通阶段不适用) | 精度 | 显存 | 延迟 | 质量 | |---|---|---|---| | FP16 | 基准 | 基准 | 基准 | | INT8 | -50% | +5–10% | 微降(对话场景通常可接受) | | INT4 | -75% | +15–25% | 明显下降,慎用 | **推荐:链路走通阶段不做 INT8 量化(关键技术决策 #5 已由外决 #4 取消):** - 理由:链路走通阶段由 DashScope 默认精度承载,精度与量化方案**不由本架构决定**(本架构不直接持有推理资源,无量化操作面) - 备选:INT8 量化作为**自托管阶段**的备选 — 仅当链路走通后启动自托管评估时一并考虑 - 当前不适用:本架构侧无量化操作面,所有量化决策由 DashScope 服务端内部决定 --- ## 七、音频上下文组织方式 ### 7.1 结构 ``` [环形缓冲:最近 N 秒音频特征] ← 持续写入,覆盖最旧帧 │ ├──> [关键帧标记] ← 强打断意图、情绪剧变等永久锚点 │ └──> [隐式摘要层] ← 每 K 秒聚合一次,可丢弃中间帧 (云 API 下由 DashScope 内部处理;通道层不感知、不干预) ``` ### 7.2 写入策略 - 每 100ms 写入一个分片(与输入分片对齐) - 滑动窗口大小:30–60s(见 §六.2 决策 #3) - 关键帧标记:由基础打断 / 节律感知的「关键事件」触发(只标记,不复制音频) ### 7.3 读取策略 - 模型推理侧(DashScope)需要时,从环形缓冲读取最近 N 秒的音频特征 - 关键帧标记在读取时一并送入(让模型知道「这里发生过重要事件」) - 隐式摘要层**对通道侧不可见** — 它属于 DashScope 内部输入预处理,本模块只负责送原始音频分片;**通道层不感知、不干预** ### 7.4 一句话总结 > **音频上下文 = 滑动窗口(原始) + 关键帧标记(永久锚点) + 隐式摘要(模型侧预处理)。三者职责分离:通道层只管滑动窗口,关键标记由事件触发,摘要由 DashScope 内部处理。** --- ## 八、与基础打断、节律感知的接口契约(回答 ④) ### 8.1 接口契约一览 | 接口 | 方向 | 内容 | 消费者 | |---|---|---|---| | **音频流分发** | 本模块 → 下游 | `audio_chunk_in` 复制品 | 基础打断、节律感知、对话 NLU | | **VAD 事件** | 本模块 → 下游 | `vad_event` | 基础打断、节律感知、对话 NLU | | **TTS 播放状态** | 本模块 → 下游 | `tts_play_state` | 基础打断(主消费者)、节律感知 | | **用户话轮事件** | 本模块 → 下游 | `user_turn_started / ended` | 节律感知、对话状态机 | | **暂停/恢复指令** | 下游 → 本模块 | `tts.pause / tts.resume` | 基础打断(主消费者) | | **节律调节参数(可选)** | 下游 → 本模块 | `rhythm_hint`(见 §九) | 节律感知(生产者) | ### 8.2 与基础打断的契约兑现 承接基础打断 §七 中的约定,本模块负责: - **提供** `audio_chunk_in`、`vad_event`、`tts_play_state` - **接收** `tts.pause / tts.resume` 并执行 本模块**不直接执行 TTS 物理暂停** — 它只冻结自己的输出流读取,TTS 物理侧的截断由 TTS 控制器执行(此为选型层,本模块不评估)。 ### 8.3 与节律感知的契约兑现 - **提供** `audio_chunk_in`(原始音频)、`vad_event`、`user_turn_started/ended` - 理由:催收对话中,Bot 的回应主要依赖「最近几秒」的用户发言 + 全文语义;音频上下文的「远因」可以通过文本上文(由模型自身维护)补偿 - 备选:若显存极度紧张,采用摘要压缩;但会增加 ~50ms 的摘要推理开销,挤压首 token 延迟预算 ### 6.3 自托管 vs API 调用 | 方案 | 延迟 | 成本 | 灵活性 | |---|---|---|---| | 自托管(GPU) | **低(可控)** | 高(CAPEX + OPEX) | 高 | | 调云 API | 中(受服务商网络与排队影响) | 低(按量) | 低 | **推荐自托管(关键技术决策 #4):** - 理由:首 token 延迟决定催收对话体验,自托管是唯一可控路径 - 备选:试点期可调 API 验证模型能力,转产前迁移到自托管 ### 6.4 量化等级 | 精度 | 显存 | 延迟 | 质量 | |---|---|---|---| | FP16 | 基准 | 基准 | 基准 | | INT8 | -50% | +5–10% | 微降(对话场景通常可接受) | | INT4 | -75% | +15–25% | 明显下降,慎用 | **推荐 INT8(关键技术决策 #5):** 显存减半、首 token 延迟可接受、对话质量损失有限。 --- ## 七、音频上下文组织方式 ### 7.1 结构 ``` [环形缓冲:最近 N 秒音频特征] ← 持续写入,覆盖最旧帧 │ ├──> [关键帧标记] ← 强打断意图、情绪剧变等永久锚点 │ └──> [隐式摘要层] ← 每 K 秒聚合一次,可丢弃中间帧 ``` ### 7.2 写入策略 - **输入方向:** 通道侧持续把分片音频送入模型输入流 - **输出方向:** 通道侧持续从模型输出流读取音频分片,推给 TTS 输出端 - **状态方向:** 模型自身维护对话上文(包括音频上文);通道侧不持有对话状态,只持有「传输态」(流 ID、时钟、缓冲水位) **通道侧不解释音频含义** — 它只搬运。这是它能保持简单、且与基础打断/节律感知解耦的关键。 --- ## 三、流式音频组织(回答 ① — 「音频如何组织」) ### 3.1 输入分片策略 | 参数 | 建议值 | 理由 | |---|---|---| | 采样率 | 16kHz 单声道 | 语音对话标准;低于 16kHz 损失高频辅音,高于则带宽浪费 | | 帧长(物理帧) | 20ms | 通用 VoIP 帧长,与 RTP 标准对齐 | | 分片(逻辑 chunk) | 100ms / 5 物理帧 | 太小则模型推理调用频繁(开销↑),太大则首 token 等待变长 | | 分片缓冲 | 自适应 80–120ms | 网络抖动时自动调整,以「稳定节奏」喂模型 | **为什么是 100ms 而不是 200ms 或 50ms:** - 50ms:模型推理调用频次翻倍,GPU 调度开销变大,首 token 改善有限 - 200ms:首 token 多等 100ms,催收对话下用户能感觉到「Bot 反应慢」 - 100ms:实测上是语音流式模型的甜区(**这是经验值,非选型结论;落地时需结合模型实际行为调测**) ### 3.2 输出分片策略 | 参数 | 建议值 | 理由 | |---|---|---| | 模型输出粒度 | 音频 token 流(由模型决定) | 由模型侧产出节奏决定 | | 通道侧输出帧 | 20ms 物理帧,与输入对齐 | 与 VoIP 接收端对齐,免去重采样 | | 输出缓冲 | 60–80ms FIFO | 让用户感觉「自然连续」,避免分片感 | ### 3.3 双向时钟 - **输入时钟:** 远端 RTP 时间戳(单调递增) - **输出时钟:** 本机生成的输出时间戳(由模型产出节奏驱动) - **两端不同步** — 这是全双工的固有特性,不需要做时钟对齐 - **通道侧只做单调性检查:** 检测 RTP 时间戳乱序、重传 ### 3.4 流式输入/输出协议契约 | 契约 | 字段 | 说明 | |---|---|---| | `audio_chunk_in` | stream_id, seq, sample_rate, samples(pcm16), timestamp | 上游送入,本模块消费 | | `audio_chunk_out` | stream_id, seq, sample_rate, samples(pcm16), bot_tts_id | 本模块产出,下游(TTS 端)消费 | | `vad_event` | stream_id, state(start/end), confidence, timestamp | 本模块产出,VAD 事件 | | `tts_play_state` | stream_id, state(playing/paused/aborted), bot_tts_id | 本模块产出,广播给订阅方 | 这些是**通道与外界的接口契约**,所有数字字段在本模块内做严格单调性 / 越界 / 错位校验。 --- ## 四、首包延迟目标与瓶颈分析(回答 ②) ### 4.1 首包延迟定义 「首包延迟」= 用户说完一句话后,到 Bot 第一个音频 token 被 TTS 输出端接收为止的时间。 — 这是催收对话「自然不卡顿」的体感指标。 ### 4.2 目标 **首包延迟 ≤ 800ms**(经验阈值,用户感知「对方在思考」而非「对方卡了」的下限)。 **争取 ≤ 600ms**(若模型推理首 token 性能可达成)。 ### 4.3 瓶颈拆解(量化估计,假设 A100/A10 级 GPU 部署) | 环节 | 估计时延 | 是否可优化 | |---|---|---| | 前端 RTP 解包 + VAD 帧 | 20–40ms | 受前端硬件限制,优化空间小 | | 流式音频分片缓冲(等齐 100ms) | 80–120ms | **可调** — 调小分片可压到 50ms,但模型推理调用频次上升 | | **模型推理首 token** | **300–500ms** | **主要瓶颈** — 占整个延迟的 50%+ | | 首段音频解码 + 重采样 | 20–40ms | 与 TTS 选型耦合,本模块不评估 | | 网络回传(机房内/跨机房间) | 20–60ms | 受部署拓扑影响 | | **合计** | **440–760ms** | — | ### 4.4 瓶颈结论(回答 ②) **最大瓶颈是「模型推理首 token」**,占端到端首包延迟的 50%+。 — 网络、前端均可控;只有模型推理延迟取决于 GPU 选型、批处理策略、量化等级。 — **降低首 token 延迟的杠杆都在模型部署侧**(§六),不在通道侧。 ### 4.5 一句话回答 ② > **瓶颈在模型推理首 token(300–500ms,占 50%+);前端 + 网络 + 分片缓冲合计 ~150–260ms,优化空间有限。要进一步压低首包延迟,必须在模型部署侧下功夫(§六),通道层只能稳住 150ms 量级。** --- ## 五、与 VAD/对话管理的协同方式 ### 5.1 VAD 协同 - **VAD 由本模块内置:** 通道侧运行轻量级 VAD(声学帧级,见基础打断 §二中的 VAD 阈值) - **VAD 事件广播:** 本模块把 `vad_event` 同时分发给基础打断、节律感知、对话 NLU 三个下游 - **不强求一致:** 各下游可以基于自己的需要做二次判定(基础打断有 400ms 候选窗口,见基础打断 §三) ### 5.2 对话管理协同 - **对话状态机的载体是对话主流程,** 不在本模块 - **本模块向状态机上报的事件:** - `user_turn_started` / `user_turn_ended`(基于 VAD 聚合) - `bot_turn_started` / `bot_turn_ended`(基于 TTS 播放状态) - **本模块从状态机接收的事件:** - `end_call`(通话终止) - 其它控制事件(略,非本模块核心) ### 5.3 与基础打断的协同(契约兑现) 兑现基础打断 §七 中约定的契约: | 流向 | 契约 | 协议字段 | |---|---|---| | 本模块 → 基础打断 | TTS 播放状态广播 | `tts_play_state: {state: playing/paused}` | | 基础打断 → 本模块 | 暂停/恢复指令 | `tts.pause(stream_id, last_sentence_idx)` / `tts.resume(stream_id, from_sentence_idx)` | | 本模块 → 基础打断 | 音频流(单写多读) | `audio_chunk_in` 复制品 | | 本模块 → 基础打断 | VAD 事件 | `vad_event` | 本模块收到 `tts.pause` 后的动作: 1. 立即停止从模型输出流读取音频分片(本模块侧冻结) 2. 广播 `tts_play_state: paused` 3. 等待 `tts.resume` 后,从 `from_sentence_idx` 对应的输出流位置继续读取 --- ## 六、模型推理部署折衷(回答 ③) ### 6.1 吞吐 vs 延迟 vs 成本(三角权衡) ``` 低延迟 /\ / \ / \ / \ / ★ \ / 折衷点 \ / \ /______________\ 高吞吐 ←———————→ 低成本 ``` - **低延迟区:** 单请求不批处理,GPU 利用率低,成本最高 - **高吞吐区:** 大 batch,延迟上升,但单请求成本最低 - **折衷点:** 持续批处理(continuous batching) — 边进边出,延迟接近单请求,吞吐接近批处理 **推荐折衷:持续批处理(关键技术决策 #2)**,目标延迟预算 ≤800ms。 ### 6.2 上下文窗口 vs 内存 | 策略 | 窗口长度 | 显存占用 | 适用 | |---|---|---|---| | 全保留 | 全通话(可能 5+ 分钟) | O(分钟数) | 不推荐 — 催收单通 3–10 分钟 | | 滑动窗口 | 最近 30–60s 原始特征 | O(常数) | **推荐 — 催收对话的「近因效应」足够** | | 摘要压缩 | 每 30s 做一次隐式摘要 | O(摘要数) | 备选 — 显存更省但工程复杂 | **推荐滑动窗口(关键技术决策 #3):** - 理由:催收对话中,Bot 的回应主要依赖「最近几秒」的用户发言 + 全文语义;音频上下文的「远因」可以通过文本上文(由模型自身维护)补偿 - 备选:若显存极度紧张,采用摘要压缩;但会增加 ~50ms 的摘要推理开销,挤压首 token 延迟预算 ### 6.3 自托管 vs API 调用 | 方案 | 延迟 | 成本 | 灵活性 | |---|---|---|---| | 自托管(GPU) | **低(可控)** | 高(CAPEX + OPEX) | 高 | | 调云 API | 中(受服务商网络与排队影响) | 低(按量) | 低 | **推荐自托管(关键技术决策 #4):** - 理由:首 token 延迟决定催收对话体验,自托管是唯一可控路径 - 备选:试点期可调 API 验证模型能力,转产前迁移到自托管 ### 6.4 量化等级 | 精度 | 显存 | 延迟 | 质量 | |---|---|---|---| | FP16 | 基准 | 基准 | 基准 | | INT8 | -50% | +5–10% | 微降(对话场景通常可接受) | | INT4 | -75% | +15–25% | 明显下降,慎用 | **推荐 INT8(关键技术决策 #5):** 显存减半、首 token 延迟可接受、对话质量损失有限。 --- ## 七、音频上下文组织方式 ### 7.1 结构 ``` [环形缓冲:最近 N 秒音频特征] ← 持续写入,覆盖最旧帧 │ ├──> [关键帧标记] ← 强打断意图、情绪剧变等永久锚点 │ └──> [隐式摘要层] ← 每 K 秒聚合一次,可丢弃中间帧 ``` ### 7.2 写入策略 - 每 100ms 写入一个分片(与输入分片对齐) - 滑动窗口大小:30–60s(见 §六.2 决策 #3) - 关键帧标记:由基础打断 / 节律感知的「关键事件」触发(只标记,不复制音频) ### 7.3 读取策略 - 模型推理侧需要时,从环形缓冲读取最近 N 秒的音频特征 - 关键帧标记在读取时一并送入(让模型知道「这里发生过重要事件」) - 隐式摘要层**对通道侧不可见** — 它属于模型输入预处理,本模块只负责送原始音频分片 ### 7.4 一句话总结 > **音频上下文 = 滑动窗口(原始) + 关键帧标记(永久锚点) + 隐式摘要(模型侧预处理)。三者职责分离:通道层只管滑动窗口,关键标记由事件触发,摘要由模型侧处理。** --- ## 八、与基础打断、节律感知的接口契约(回答 ④) ### 8.1 接口契约一览 | 接口 | 方向 | 内容 | 消费者 | |---|---|---|---| | **音频流分发** | 本模块 → 下游 | `audio_chunk_in` 复制品 | 基础打断、节律感知、对话 NLU | | **VAD 事件** | 本模块 → 下游 | `vad_event` | 基础打断、节律感知、对话 NLU | | **TTS 播放状态** | 本模块 → 下游 | `tts_play_state` | 基础打断(主消费者)、节律感知 | | **用户话轮事件** | 本模块 → 下游 | `user_turn_started / ended` | 节律感知、对话状态机 | | **暂停/恢复指令** | 下游 → 本模块 | `tts.pause / tts.resume` | 基础打断(主消费者) | | **节律调节参数(可选)** | 下游 → 本模块 | `rhythm_hint`(见 §九) | 节律感知(生产者) | ### 8.2 与基础打断的契约兑现 承接基础打断 §七 中的约定,本模块负责: -
